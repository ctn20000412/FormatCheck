# Document IO Methods For Format Checking

Use this reference before invoking the LLM. The checker must compare rules against extracted document evidence, not raw binary files.

## Inputs

The preferred standard input is `format_rule.json` generated by `extract-format-rules`. If the standard is still a document file, first extract rules using the same mature document IO methods described in `extract-format-rules/references/document_io_methods.md`.

The preferred paper input is `.docx`. Current project requirements only support `.docx` for checked papers because native Word comments must be written into a copy of the source document.

## DOCX Paper Evidence Method

Use `python-docx` for high-level document structure:

- Paragraph index, text, style name, alignment, indentation, spacing where exposed.
- Runs, direct font family, size, bold, italic, underline, color where exposed.
- Tables, rows, cells, table text, nearby captions.
- Sections exposed by `python-docx`.

Use direct WordprocessingML inspection for accurate formatting:

- `word/document.xml`
  - Section properties: `w:sectPr`, `w:pgSz`, `w:pgMar`, columns, header/footer references.
  - Paragraph properties: `w:pPr`, `w:pStyle`, `w:jc`, `w:ind`, `w:spacing`, `w:numPr`.
  - Run properties: `w:rPr`, `w:rFonts`, `w:sz`, `w:b`, `w:i`, `w:color`.
- `word/styles.xml`
  - Default paragraph/run properties.
  - Named style definitions and `w:basedOn` inheritance.
  - Heading styles and body styles.
- `word/numbering.xml`
  - Heading numbering and list numbering definitions.
- `word/header*.xml` and `word/footer*.xml`
  - Header/footer text and page number fields.

Resolve effective formatting in this order:

1. Direct run/paragraph property.
2. Paragraph or character style.
3. Based-on style chain.
4. Document defaults.
5. Theme defaults only when explicitly needed.

Record both `actual` raw values and normalized values. Examples:

- Twips to millimeters: `mm = twips * 25.4 / 1440`.
- Twips to points: `pt = twips / 20`.
- Half-points: `pt = value / 2`.
- Word line-spacing values: keep raw XML value and readable interpretation.

## DOCX Visual Verification

When page layout, page numbers, headers/footers, table overflow, or figure placement matters, render the document before finalizing:

1. Convert DOCX to PDF with LibreOffice headless if available.
2. Render PDF pages to PNG with Poppler.
3. Inspect rendered pages for clipping, overlapping text, missing page numbers, and table/figure layout.

If bundled `doc` skill utilities are available, prefer its `scripts/render_docx.py` helper for visual checks. If rendering is unavailable, still perform XML/property checks and state the remaining layout risk.

## PDF Standard Evidence Method

When a standard source is PDF:

- Use `pdfplumber` to extract text and tables by page.
- Use `pypdf` for page count and metadata.
- Render pages with Poppler (`pdftoppm`) to verify layout and table extraction quality.
- Use OCR only when the PDF is scanned and an OCR engine is available.

Do not infer exact Word font sizes or margins from PDF appearance unless the PDF text explicitly states them. Mark inferred PDF-layout evidence with low or medium confidence.

## Native Word Comments

Annotated output must be a copy of the paper. Never overwrite the original.

Use native Word comments by editing the DOCX package:

- Add or update `word/comments.xml`.
- Ensure `word/_rels/document.xml.rels` has a comments relationship.
- Ensure `[Content_Types].xml` has a comments override.
- Mark the anchor paragraph with `w:commentRangeStart`, `w:commentRangeEnd`, and `w:commentReference`.

Preferred comment anchors:

1. Exact `anchor_text` found in a paragraph.
2. `location.quote`.
3. `location.paragraph_index`.

If no anchor is found, keep the issue in `format_check_analysis.docx`, list it as unplaced, and set `need_manual_confirmation: true`.

Every comment must follow this exact text structure:

```text
错误原因：<why this is wrong>
规范要求：<required rule>
修改建议：<specific correction>
```

## Evidence Package Shape

Build a paper-evidence object before prompting:

```json
{
  "paper_file": {
    "path": "string",
    "file_name": "string",
    "file_type": "docx",
    "selected_parser": "docx-python-docx-ooxml"
  },
  "extraction_quality": {
    "text_complete": true,
    "format_properties_complete": true,
    "layout_rendered": false,
    "warnings": []
  },
  "page_setup": [],
  "styles": [],
  "paragraphs": [
    {
      "paragraph_index": 1,
      "section": "string",
      "style": "Heading 1",
      "text": "string",
      "effective_format": {}
    }
  ],
  "tables": [],
  "figures": [],
  "headers_footers": [],
  "citations_references": []
}
```

Keep evidence compact but sufficient for deterministic rule comparison.

## Quality Gates

- Do not ask the LLM to inspect a raw DOCX/PDF binary directly.
- Do not flag a deterministic Word-format issue unless extracted properties show the mismatch.
- Do not generate a comment without a concrete issue, rule requirement, and correction suggestion.
- Do not deliver the annotated DOCX until comments are written to a copy and the output file opens as a valid DOCX package.
