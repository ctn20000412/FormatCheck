# 双流程检测架构设计

## 目标

在现有系统基础上增加第二套检测流程，使用户可以选择不同流程完成论文格式检查，并对比两种流程的检查结果、稳定性和准确率。

系统保留当前 LLM 主导流程，同时新增“程序确定性检查 + LLM 解释生成”的混合流程。

## 一、两种流程定义

### 流程 A：LLM 主导检测流程

当前系统主要采用该流程。

流程：

```text
上传规范文件 + 上传待检测论文
        ↓
Agent1 使用 LLM 抽取 format_rule.json
        ↓
Python 提取 docx 文本和格式证据
        ↓
Agent2 将 format_rule + docx evidence + 论文全文发送给 LLM
        ↓
LLM 判断错误、生成统计、生成批注内容
        ↓
Python 写入分析文档和批注版论文
```

特点：

- 优点：
  - 实现简单。
  - 对自然语言规范理解能力较强。
  - 对模糊规则、语义问题、错别字和语法问题更友好。

- 缺点：
  - 字体、字号、页边距、行距等确定性规则容易被 LLM 漏判或误判。
  - 大论文上下文很长，成本高、速度慢。
  - LLM 输出不稳定，JSON 结构可能出错。
  - 难以保证每次检查结果一致。

适用场景：

- 早期验证。
- 规则较模糊。
- 需要快速生成解释性报告。
- 对准确率要求不是极高的初筛任务。

建议流程标识：

```json
{
  "workflow": "llm_direct"
}
```

### 流程 B：混合确定性检测流程

新增推荐流程。

流程：

```text
上传规范文件 + 上传待检测论文
        ↓
Agent1 使用 LLM 抽取原始规则
        ↓
规则标准化器将规则转换为可执行 rule schema
        ↓
Python 使用 WordprocessingML 精确提取论文格式事实
        ↓
Python 确定性检查器执行硬规则检查
        ↓
LLM 只处理语义规则、模糊规则、错别字、语法和解释文本
        ↓
合并程序检查结果 + LLM 语义检查结果
        ↓
生成统计分析文档和批注版论文
```

特点：

- 优点：
  - 字体、字号、页边距、行距、缩进、标题编号、表格边框等硬规则更准确。
  - LLM 不再负责猜测格式事实，幻觉更少。
  - 检查结果更稳定，可重复。
  - 大量格式错误可由本地程序快速完成，减少 token 消耗。

- 缺点：
  - 需要额外开发规则标准化器和确定性检查器。
  - 对无法标准化的规则仍需要 LLM 或人工确认。
  - 页码、分页、目录页码等仍需要渲染引擎增强。

适用场景：

- 正式检测。
- 论文格式规则明确。
- 需要较高准确率和可解释证据。
- 需要降低 LLM 成本和不稳定性。

建议流程标识：

```json
{
  "workflow": "hybrid"
}
```

## 二、前端交互设计

在当前模型选择区域下方增加“检测流程”选择。

建议选项：

```text
检测流程：
[ LLM 主导检测 ] [ 程序精确检测 + LLM 解释 ]
```

默认值：

```text
程序精确检测 + LLM 解释
```

另可增加一个实验选项：

```text
[ 同时运行两种流程并对比 ]
```

对应 workflow：

```json
{
  "workflow": "compare"
}
```

三种模式：

| 前端选项 | workflow | 含义 |
| --- | --- | --- |
| LLM 主导检测 | `llm_direct` | 使用现有流程 |
| 程序精确检测 + LLM 解释 | `hybrid` | 使用新增推荐流程 |
| 同时运行两种流程并对比 | `compare` | 分别运行两套流程，生成差异报告 |

## 四、Python Agent 设计

### 1. 主入口分发

新增 workflow 分发：

```python
def run_request(request):
    workflow = request.get("workflow", "llm_direct")

    if workflow == "llm_direct":
        return run_llm_direct_workflow(request)

    if workflow == "hybrid":
        return run_hybrid_workflow(request)

    if workflow == "compare":
        return run_compare_workflow(request)

    raise ValueError("Unsupported workflow")
```

### 2. LLM 主导流程

保留现有逻辑：

```python
run_llm_workflow(...)
```

输出：

```json
{
  "workflow": "llm_direct",
  "statistics": {},
  "issues": [],
  "accuracy_evidence": {
    "source": "llm_judgement",
    "deterministic_issue_count": 0,
    "llm_issue_count": 0
  }
}
```

### 3. 混合流程

新增核心模块：

```text
agent-service/app/rule_normalizer.py
agent-service/app/docx_evidence.py
agent-service/app/deterministic_checker.py
agent-service/app/issue_merger.py
```

流程：

```python
raw_rules = extract_format_rules_with_llm(standard_file)
normalized_rules = normalize_rules(raw_rules)
docx_evidence = build_docx_analysis_evidence(checked_file)
deterministic_issues = run_deterministic_checks(normalized_rules, docx_evidence)
semantic_issues = run_llm_semantic_checks(unhandled_rules, docx_evidence, checked_text)
issues = merge_issues(deterministic_issues, semantic_issues)
```

## 五、规则标准化设计

Agent1 原始输出需要转换为固定结构。

标准 rule schema：

```json
{
  "rule_id": "R001",
  "category": "font_and_size",
  "scope": "body_paragraph",
  "target_object": "paragraph_run",
  "property": "east_asia_font",
  "operator": "equals",
  "expected_value": "宋体",
  "unit": null,
  "check_method": "deterministic",
  "source_text": "正文采用宋体小四号",
  "confidence": "high",
  "need_manual_confirmation": false
}
```

`check_method` 分类：

| check_method | 含义 | 示例 |
| --- | --- | --- |
| `deterministic` | Python 可直接判断 | 字体、字号、页边距、行距 |
| `llm_semantic` | 需要 LLM 判断 | 摘要内容是否完整、错别字 |
| `render_required` | 需要渲染引擎 | 页码位置、目录页码、分页 |
| `manual` | 需要人工确认 | 规范表述不明确 |

## 六、确定性检查器设计

第一阶段建议支持以下规则：

| 类别 | 可检查项 |
| --- | --- |
| 页面设置 | 纸张大小、页边距、方向、页眉页脚距离 |
| 字体字号 | 中文字体、英文字体、字号、加粗、斜体、颜色 |
| 段落格式 | 首行缩进、左缩进、右缩进、行距、段前段后、对齐方式 |
| 标题编号 | 标题样式、编号层级、是否居中、是否加粗 |
| 表格格式 | 边框、行列数、表格文本、表格标题位置 |
| 页眉页脚 | 页眉文本、页脚文本、字段 |

确定性 issue 示例：

```json
{
  "issue_id": "D001",
  "source": "deterministic_checker",

  "severity": "medium",
  "location": {
    "page": null,

    "paragraph_index": 12,

  },
  "rule_id": "R003",
  "expected": "宋体",
```

## 七、双流程对比模式

当 workflow 为 `compare` 时：

```text
运行流程 A：llm_direct
运行流程 B：hybrid
生成 compare_result.json
生成对比分析文档
```

对比维度：

| 指标 | 含义 |
| --- | --- |
| issue_count_a | LLM 主导流程发现的问题数 |
| issue_count_b | 混合流程发现的问题数 |
| matched_issue_count | 两流程都发现的问题数 |
| only_llm_count | 只有 LLM 发现的问题数 |
| only_hybrid_count | 只有混合流程发现的问题数 |
| deterministic_high_confidence_count | 程序确定性高置信问题数 |
| manual_confirmation_count | 需要人工确认的问题数 |
| rule_coverage | 已检查规则覆盖率 |

对比输出：

```json
{
  "workflow": "compare",
  "summary": {
    "llm_direct_issue_count": 18,
    "hybrid_issue_count": 24,
    "matched_issue_count": 12,
    "only_llm_count": 6,
    "only_hybrid_count": 12,
    "recommended_workflow": "hybrid"
  },
  "accuracy_analysis": {
    "higher_confidence_workflow": "hybrid",
    "reason": "混合流程包含 16 条程序确定性高置信格式错误，LLM 主导流程漏检了部分字号和行距问题。"
  }
}
```

## 八、准确率判断方式

需要注意：没有人工标注的标准答案时，系统不能严格计算真实准确率，只能计算“相对可靠性指标”。

### 1. 没有人工标注时

可使用以下指标估计：

```text
准确性倾向 = 高置信确定性问题数 + 两流程一致问题数 - 低置信问题数
```

推荐展示：

```text
流程 A：LLM 主导检测
- 发现问题：18
- 高置信：8
- 需要人工确认：7

流程 B：程序精确检测 + LLM 解释
- 发现问题：24
- 高置信：18
- 需要人工确认：3

建议采用：流程 B
原因：流程 B 的确定性证据更多，低置信问题更少。
```

### 2. 有人工标注时

如果后续建立人工标注集，可以计算真实指标：

```text
Precision = 正确检出的问题数 / 系统检出的问题数
Recall = 正确检出的问题数 / 人工标注问题总数
F1 = 2 * Precision * Recall / (Precision + Recall)
```

建议建立测试集：

```text
sourceFIle/benchmark/
  case001/
    standard.docx
    paper.docx
    ground_truth.json
```

`ground_truth.json` 示例：

```json
{
  "issues": [
    {
      "category": "font_and_size",
      "paragraph_index": 5,
      "expected": "宋体小四",
      "actual": "黑体小四"
    }
  ]
}
```

## 十、推荐实施顺序

1. 增加 `workflow` 参数，前端可选流程。
2. 保留现有流程为 `llm_direct`。
3. 新增 `hybrid` 空壳流程，先复用现有输出结构。
4. 实现规则标准化器。
5. 实现确定性检查器第一批规则：字体、字号、页边距、行距、缩进。
6. 实现 `compare` 模式，输出差异报告。
7. 建立人工标注 benchmark，计算 Precision、Recall、F1。

## 十一、结论

两套流程并存后，系统可以同时满足“快速 LLM 初筛”和“高准确率正式检测”两个场景。

最终推荐默认使用：

```text
程序精确检测 + LLM 解释生成
```

原因是格式检查中大量规则属于确定性属性，程序读取 WordprocessingML 后直接判断更可靠。LLM 应主要负责规范理解、模糊规则判断、错别字语法检查和中文解释生成。
