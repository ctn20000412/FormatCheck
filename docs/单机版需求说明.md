# 单机版需求说明

## 1. 项目目标

本系统用于在本地完成论文格式检查。用户选择模型厂商和型号后，上传一份文档格式规范文件和一份待检测论文文件。系统先从规范文件中抽取结构化格式规则，再根据这些规则检查论文格式，最终生成可下载的规范规则文件、错误统计分析文档和批注版论文。

## 2. 系统边界

本阶段只实现单机版能力：

- 不设计数据库。
- 不设计账号、权限、多用户协作。
- 不考虑公网部署、云端上线、远程文件服务。
- 不依赖长期任务队列。
- 文件保存在本地项目目录。
- 前端下载链接指向本地应用可访问的结果文件。

## 3. 用户流程

1. 用户打开本地前端页面。
2. 用户选择模型厂商和模型型号。
3. 用户上传格式规范文件。
4. 用户上传待检测论文 `checked_file`。
5. 用户点击开始处理。
6. 系统调用 Agent1 抽取格式规范，生成 `format_rule.json`。
7. 前端展示 `format_rule.json` 下载链接。
8. 系统调用 Agent2 检查论文格式。
9. 系统生成错误统计分析文档和批注版论文。
10. 前端展示错误统计分析数据，并提供两个结果文件下载链接。

## 4. 输入

| 输入 | 说明 | 支持格式 |
| --- | --- | --- |
| 模型厂商 | 用户选择调用哪个 LLM 提供方 | 本地配置决定 |
| 模型型号 | 用户选择具体模型 | 本地配置决定 |
| 格式规范文件 | 记录论文格式、排版、引用、章节等要求 | `.pdf`、`.doc`、`.docx`、`.md`、`.txt` |
| 待检测论文 | 需要进行格式检查的论文 | 优先 `.docx` |

## 5. 输出

| 输出 | 文件名建议 | 说明 |
| --- | --- | --- |
| 格式规范 JSON | `format_rule.json` | Agent1 从规范文件抽取出的结构化规则 |
| 错误统计分析文档 | `format_check_analysis.docx` | 面向用户查看的错误统计与明细 |
| 批注版论文 | `checked_file_annotated.docx` | 在论文副本中用 Word 批注标出错误 |
| 检查结果 JSON | `format_check_result.json` | 前端展示统计数据使用的结构化结果 |

## 6. 核心功能

### 6.1 模型选择

前端提供模型厂商和型号选择控件。后端或本地服务根据选择结果构造 LLM 调用配置。

### 6.2 格式规则抽取

Agent1 使用 `extract_rule_prompt` 和 `extract-format-rules` skill，从格式规范文件中提取规则，保存为 `format_rule.json`。

### 6.3 论文格式检查

Agent2 使用 `format_rule.json` 和 `checked_file`，调用 `check-paper-format` skill，输出错误列表、统计数据和批注内容。

### 6.4 文件生成与下载

系统将所有结果文件保存到以待检测文档名命名的本地结果目录。前端展示下载链接，不覆盖用户上传的原始文件。

## 7. 非目标

- 不做论文内容质量评价。
- 不做查重。
- 不自动修改原论文正文。
- 不支持多人同时任务管理。
- 不做长期历史记录管理。

## 8. 已确认技术与业务约束

### 8.1 技术栈

| 层级 | 技术 |
| --- | --- |
| 前端 | Vue |
| Java 后端 | Spring Boot，负责对前端提供接口、接收上传、返回任务状态和下载链接 |
| Python 服务 | 负责和 LLM 外部 API 交互、执行 Agent、解析文档、生成结果文件 |

Java 不直接和 LLM 交互。Java 使用 `ProcessBuilder` 启动 Python 脚本，并通过本地 JSON 请求/响应文件或标准输出交换数据。

### 8.2 模型厂商

前端提供以下模型厂商选择：

- `deepseek`
- `chatgpt`
- `claudecode`
- `kimi`
- `glm`

模型通过外部 API 调用。API Key 和 Base URL 在 Python 配置中维护，前端不提供 key/url 配置入口，也不支持用户调整 temperature、max_tokens 等高级参数。

### 8.3 文件格式

| 文件 | 支持范围 |
| --- | --- |
| 格式规范文件 | 必须支持 `.pdf`、`.doc`、`.docx`、`.md` |
| 待检测论文 | 当前只支持 `.docx` |

### 8.4 检查方式

- 文档格式规则尽量由程序读取 Word 样式、页边距、字体、字号、段落、标题、表格、页眉页脚等属性后进行判断。
- 所有可程序化的格式规则优先使用程序检查。
- 错别字和语法错误由 LLM 判断。
- LLM 不应替代程序去猜测 Word 已能直接读取的格式属性。

### 8.5 输出要求

- 错误统计分析文档格式为 `.docx`。
- 批注版论文必须使用 Word 原生批注。
- 批注内容格式固定为：`错误原因 + 规范要求 + 修改建议`。
- 前端展示错误明细表。
- 前端不预览原始文件，但必须保存原始上传文件并提供需要的下载结果。
- 不允许用户在前端手动修改 `format_rule.json` 后继续检查。

### 8.6 文件保存

结果目录不以 session 命名，而是以待检测文档名字命名。结果保留，不自动清理。

目录内部按五类内容组织：`待检测文件`、`规则规范文件`、`规则抽取结果`、`检测结果`、`检测后带批注的源文件`。
