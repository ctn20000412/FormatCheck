# 产品需求文档（PRD）

## 1. 文档信息

- 产品名称：开发文档规范检查项目
- 文档版本：V1.0
- 目标版本：V1.0
- 编写日期：2026-04-21

## 2. 项目背景

团队在编写技术方案、开发说明、接口文档、测试文档等交付物时，经常存在格式不统一、排版不符合规范、章节结构不完整的问题。人工逐项校对效率低、标准不一致、复用差。

本项目通过引入两个 Agent：

- 规则抽取 Agent：将规范文档提炼为结构化规则
- 格式检查 Agent：根据结构化规则检查待审文档并产出修正建议

两个 Agent 的输入方式统一为“提示词 + 原始上传文件”。系统不要求在调用 Agent 前先将文档解析为纯文本再传给 LLM。

实现从“规则准备”到“自动检查”的闭环。规则准备既可以来自规范文档抽取，也可以直接导入已有规则文件。

## 3. 产品目标

- 将复杂、自然语言形式的规范文档转化为可执行规则文件
- 支持直接复用已有 `完整规范.js`，减少重复抽取和人工确认成本
- 允许用户对抽取结果进行人工校验和修订，降低 LLM 抽取偏差风险
- 自动检查待审文档的格式问题并给出明确整改建议
- 在原文中写入批注，降低人工对照修改成本
- 所有产物按检查会话独立归档，便于追溯

## 4. 用户角色

### 4.1 文档管理员

- 上传标准规范文档
- 审核与修订抽取规则
- 维护组织内通用规范模板

### 4.2 文档编写人员

- 上传待检查文档
- 查看检查报告
- 下载带批注文档并完成修订

### 4.3 项目负责人 / 质量负责人

- 审阅检查结果
- 监督规范执行情况

## 5. 术语定义

- 规范文档：包含排版、格式、章节、标题、编号、字体、页边距等要求的标准文件
- `规范.js`：规则抽取 Agent 输出的中间结构化规则文件，供前端人工确认
- `完整规范.js`：用户确认后的最终规则文件，或用户直接上传并通过系统校验的规则文件，供格式检查 Agent 使用
- 规则项：规则文件中的最小检查单元，用于定义“检查谁、检查什么、严重程度、依据、适用范围”
- 检查报告：待检查文档的错误列表、原因说明、修正建议集合
- 批注文档：在原始待检查文档基础上写入问题批注后的新文件
- 会话目录：系统为一次规范抽取或一次检查任务生成的独立文件夹

## 6. 产品范围

### 6.1 本期范围

- 上传规范文档并调用 LLM 完成规范抽取
- 或直接上传 `完整规范.js`
- 生成并展示 `规范.js`
- 用户在线修改规则内容
- 生成或导入 `完整规范.js`
- 上传待检查文档
- 调用 LLM 基于 `完整规范.js` 执行格式检查

- 生成带批注的文档副本

### 6.2 暂不纳入本期

- 用户、角色、权限体系
- 数据库持久化
- 多租户与组织级规则库
- 文档内容语义正确性检查
- 历史版本对比分析
- Office 在线预览编辑

## 7. 核心业务场景

### 7.1 场景一：从规范文档生成可执行规则

用户上传《文档编写规范》后，系统调用规则抽取 Agent，抽取标题层级、字体字号、行距、页边距、编号规则、图片表格标题规范等要求，生成 `规范.js`。前端将其转换为表单或树形结构，用户修正后生成 `完整规范.js`。

### 7.2 场景二：直接导入已有完整规则

用户已经持有符合系统规则结构的 `完整规范.js` 时，可以直接上传该文件。系统完成文件类型和规则结构校验后，直接将其作为最终规则文件保存，用户无需经过规则抽取和确认页面。

### 7.3 场景三：基于规则自动检查待审文档

用户上传待审文档并选择 `完整规范.js` 后，系统调用格式检查 Agent，对文档排版和格式进行逐项校验，输出错误位置、错误原因、整改建议，并生成带批注的新文档。

## 8. 功能需求

### 8.1 规则准备模块

#### 8.1.1 上传规范文件或完整规则文件

- 支持上传单个规范文档
- 支持直接上传单个 `完整规范.js`
- 支持格式：`.docx`、`.pdf`、`.md`、`.txt`
- 规则文件格式：`.js`
- 单文件大小限制可配置，建议默认 20MB
- 上传后生成唯一 `sessionId`

#### 8.1.2 规则准备模式选择

- 模式一：规范抽取模式
- 模式二：规则直传模式
- 前端应在规则准备入口明确展示两种方式

#### 8.1.3 调用规则抽取 Agent

- Java 后端负责创建会话目录和任务记录
- Java 后端调用 Python Agent 服务
- 调用规则抽取 Agent 时传入“规则抽取提示词 + 上传的规范文件”
- Agent 输出结构化规则 JSON/JS 内容
- 系统将规则写入 `规范.js`

#### 8.1.4 直接导入完整规则

- Java 后端接收用户上传的 `完整规范.js`
- 系统校验文件扩展名、文件大小与规则结构
- 校验通过后直接保存为最终规则文件
- 任务状态直接进入已确认状态

#### 8.1.5 中间规则展示与编辑
- 前端将 `规范.js` 转换为便于人工理解的页面
- 页面支持查看、修改、删除、补充规则
- 每条规则建议至少包含：
  - `rule_id`
  - `category`
  - `scope`
  - `rule_name`
  - `description`
  - `check_type`
  - `check_object`
  - `expected`
  - `severity`
  - `source_text`
  - `applicable_sections`
  - `user_confirmed`
- 支持按规则分类展示：
  - 页面设置
  - 标题样式
  - 正文样式
  - 图片与表格
  - 编号规则
  - 特殊章节要求

#### 8.1.6 生成最终规则

- 用户点击确认后生成 `完整规范.js`
- 成功生成后删除中间文件 `规范.js`
- 记录规则确认时间与版本号

### 8.2 格式检查模块

#### 8.2.1 上传待检查文档

- 支持选择一个已确认的 `完整规范.js`
- 支持选择来源于“规范抽取模式”或“规则直传模式”的最终规则
- 支持上传单个待检查文档
- 系统创建检查任务目录

#### 8.2.2 调用格式检查 Agent

- 调用格式检查 Agent 时传入“格式检查提示词 + 待检查文档 + `完整规范.js`”
- 输出结构化问题列表
- 每条问题应至少包含：
  - 位置
  - 错误类型
  - 对应规则 ID
  - 对应规则名称
  - 规则依据
  - 原因说明
  - 修正建议

#### 8.2.3 生成检查报告

- 检查报告格式建议为 `report.json` + `report.md`
- 支持前端页面查看
- 支持下载

#### 8.2.4 生成批注文档

- 系统在原文对应位置写入批注
- 输出新文件，保留原文件不覆盖
- 新文件命名建议：`原文件名.annotated.docx`

### 8.3 会话与文件管理模块

- 所有会话按独立目录存储
- 每个目录至少包含：
  - 原始输入文件
  - `规范.js` 或 `完整规范.js`
  - 检查报告
  - 批注文档
  - 任务元数据 `task.json`
- 支持查询任务状态
- 支持查看任务产物列表

## 9. 非功能需求

### 9.1 性能

- 单个文档上传响应时间小于 3 秒（不含文件传输）
- Agent 任务采用异步处理，避免阻塞接口线程
- 常规 50 页以内文档，检查任务目标完成时间小于 3 分钟

### 9.2 可用性

- 前端对上传、处理中、成功、失败状态有明确提示
- 失败任务应可查看失败原因
- Agent 输出格式异常时应支持重试

### 9.3 可维护性

- Java 与 Python 通过明确接口解耦
- Agent 提示词模板独立管理，便于后续调优
- 规则文件采用稳定结构，便于未来扩展
- 检查报告采用结构化输出，方便二次开发

### 9.4 安全性

- 文件上传需限制扩展名与 MIME 类型
- 存储目录隔离，避免路径穿越
- 日志需脱敏，不打印完整文档正文

## 10. 用户界面需求

### 10.1 页面清单

- 规范抽取页
- 规则确认编辑页
- 格式检查提交页
- 检查结果页
- 任务详情页

### 10.2 关键交互要求

- 规则确认页支持分类折叠、搜索、字段校验
- 检查结果页支持按错误类型过滤
- 报告与批注文档提供下载入口

## 11. 验收标准

### 11.1 规范抽取验收

- 上传规范文档后可成功生成 `规范.js`
- 前端可正确展示抽取规则
- 用户保存后生成 `完整规范.js`
- 原 `规范.js` 被删除
- 直接上传合法 `完整规范.js` 后可直接进入可用状态

### 11.2 格式检查验收

- 上传待检查文档后可成功执行检查
- 报告中包含错误位置、原因、整改建议
- 可生成带批注的新文档
- 所有产物均保存在对应会话目录

### 11.3 稳定性验收

- 不合法文件上传会被拒绝
- Agent 超时、失败时系统返回明确错误信息
- 前端刷新后仍可通过任务详情页查看结果

### 里程碑一：最小可用版本

- 增加规则模板复用
- 增加结果筛选与统计
