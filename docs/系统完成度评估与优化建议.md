# 系统完成度评估与优化建议

检查时间：2026-05-01

## 一、当前完成情况

### 1. 前端 Vue

完成度：约 80%

已完成：

- 支持选择模型厂商和模型型号。
- 支持上传规范文件：`.pdf`、`.doc`、`.docx`、`.md`。
- 支持上传待检测论文：当前限制为 `.docx`。
- 支持提交 `/api/tasks/check`。
- 支持展示错误统计、分类统计、严重程度统计和错误明细表。
- 支持下载格式规则 JSON、错误统计分析文档、批注版论文。

已验证：

```text
npm.cmd run build
结果：通过
```

主要不足：

- 前端仍是同步等待接口返回，长任务期间没有真实进度条、阶段状态和日志窗口。
- 错误明细表展示字段较基础，缺少按规则、章节、严重程度筛选。
- 页面中文在部分源码/终端环境中存在编码显示风险，需要统一 UTF-8 检查。

### 2. Java Spring Boot 后端

完成度：约 85%

已完成：

- 提供 `/api/tasks/check` 任务接口。
- 提供模型列表接口和文件下载接口。
- 支持文件类型校验。
- 支持按待检测文件名创建结果目录。
- 支持保存原始规范文件、待检测论文、规则抽取结果、检测结果、分析文档、批注版论文。
- Java 已改为通过 HTTP 调用常驻 Python Agent，不再每次接口调用都启动 Python 进程。

已验证：

```text
mvn test
Tests run: 7, Failures: 0, Errors: 0, Skipped: 0
BUILD SUCCESS
```

主要不足：

- 当前接口仍是同步调用 Python Agent。论文较大或模型响应慢时，浏览器请求可能超时。
- 缺少任务 ID、任务状态查询、取消任务、阶段日志查询等本地任务管理能力。
- 文件下载路径需要继续保持严格 root 校验，避免未来扩展时出现路径穿越风险。

### 3. Python Agent

完成度：约 80%

已完成：

- Python Agent 可作为常驻 HTTP 服务运行。
- Agent1 调用 `extract-format-rules` 相关提示词抽取规则。
- Agent2 调用 `check-paper-format` 相关提示词检查论文格式。
- 支持 OpenAI-compatible 流式接口。
- 支持在终端实时打印 prompt、reasoning delta、answer delta、final。
- 支持写入 `llm_interactions.jsonl`。
- 支持真实 API 配置文件和本地 key 配置文件。
- 支持将原论文复制并写入 Word 原生批注。
- 已增强 `.docx` 证据提取，读取 WordprocessingML 中的样式、编号、节、页边距、页眉页脚、字段、脚注尾注、图片、超链接、表格边框、段落和 run 属性。

已验证：

```text
python -m unittest discover -s tests -q
Ran 17 tests
OK (skipped=1)
```

主要不足：

- 规范文件 `.pdf`、`.doc`、`.md` 当前主要仍偏文本读取，PDF 版式、表格、字体证据不足。
- `.doc` 尚未接入 LibreOffice/WPS 转 `.docx` 的稳定转换链路。
- Agent2 目前按“整篇一次性发送给 LLM”的要求实现，大论文会遇到上下文长度、费用和响应时间问题。
- LLM 输出 JSON 仍依赖修复函数兜底，缺少更严格的 schema 校验和失败重试。
- 终端日志目前会完整打印 prompt，长论文时日志过大，影响性能和可读性。

### 4. Skill 与提示词

完成度：约 75%

已完成：

- `extract-format-rules` skill 已包含规范文件解析逻辑、输出 schema、成熟文档读取方法说明。
- `check-paper-format` skill 已包含检查逻辑、输出 schema、定位要求、批注内容格式要求。
- `format_check_prompt` 已要求 LLM 使用 WordprocessingML 结构化证据，不能假装执行 Python。

主要不足：

- Python 主流程中仍有一段内联 user prompt，和 skill prompt 存在重复说明，后续容易漂移。
- 两个 skill 的文档读取方法说明较完整，但 Python 生产代码尚未完全实现 PDF/DOC 的成熟读取路径。
- 缺少规则归一化层：不同模型抽取出的 rule 字段可能不一致，导致后续检查稳定性下降。

## 二、性能优化建议

优先级 P0：

1. 将 `/api/tasks/check` 从同步接口改成本地异步任务。
   - 提交任务后立即返回 `taskId`。
   - 前端轮询 `/api/tasks/{taskId}` 或使用本地 SSE。
   - Python Agent 后台执行，不阻塞浏览器请求。

2. 增加 token 预算和证据压缩层。
   - WordprocessingML 原始证据很大，应先转为“规则相关证据包”。
   - 例如规则涉及页边距时只发送 `sections`；涉及正文时发送正文段落和对应样式；涉及表格时发送 `tables`。

3. 对 Agent1 的 `format_rule` 做缓存。
   - 同一规范文件可按文件 hash 缓存规则抽取结果。
   - 重复检测不同论文时不需要重复调用 LLM 抽规则。

优先级 P1：

4. 对 LLM 调用增加超时、重试和错误分类。
   - HTTP 429、5xx、网络超时可自动重试。
   - JSON 解析失败可进行一次“仅修复 JSON”请求。

5. 限制终端日志输出长度。
   - 文件中保存完整 `llm_interactions.jsonl`。
   - 终端只显示阶段、前后若干字符、token 计数或摘要。

6. 增加本地预检查，减少 LLM 工作量。
   - 字体、字号、页边距、行距、缩进、标题样式、表格边框等可由 Python 确定性检查。
   - LLM 只处理语义规则、错别字、语法、复杂引用格式和不明确规则。

优先级 P2：

7. 增量读取和分层证据。
   - 先提取目录、标题、样式分布、异常格式段落。
   - 再按规则请求 LLM 判断，而不是一次发送全文和全部证据。

## 三、检查准确率优化建议

优先级 P0：

1. 建立规则标准化 schema。
   - Agent1 输出必须统一为：`rule_id`、`category`、`scope`、`target_object`、`property`、`expected_value`、`check_method`、`source_text`、`confidence`。
   - 禁止只输出自然语言规则，否则 Agent2 很难稳定执行。

2. 建立 Python 确定性检查器。
   - 对可程序判断的规则直接出结果。
   - 每条 issue 附带证据：段落 index、样式 id、实际值、期望值、来源 rule。
   - LLM 负责复核和生成中文解释，不负责猜测基础格式事实。

3. 引入 Word 渲染校验。
   - 当前 XML 能读取格式属性，但不能计算真实分页和渲染页码。
   - 若要检查“第几页”“页码位置”“目录页码”“跨页表格”等，需要 LibreOffice/WPS/Word COM 或渲染工具。

4. 优化批注锚点定位。
   - 当前主要按 `anchor_text` 或段落 index 放批注。
   - 应增加 run 级定位、表格单元格定位、页眉页脚定位、图片/题注定位。

优先级 P1：

5. 建立样式继承和实际显示值对照表。
   - 当前已提取部分 effective properties。
   - 后续应继续补齐主题字体、默认字体、表格样式、编号样式、列表层级继承。

6. PDF 规范解析增强。
   - 使用 `pdfplumber` 提取页面文字、表格、坐标。
   - 使用 `pypdf` 提取页数和元数据。
   - 使用 Poppler 渲染页面做版面确认。
   - 对扫描版 PDF 接 OCR。

7. DOC 规范解析增强。
   - 使用 LibreOffice headless 转 `.docx`。
   - 转换失败时明确返回错误，不要静默按二进制文本读取。

8. 建立人工确认机制。
   - 对低置信度规则和低置信度 issue 在前端标记“需人工确认”。
   - 用户可确认/忽略，作为后续规则优化样本。

## 四、建议的下一步开发顺序

1. P0：把任务接口改为异步任务模型，解决大论文长时间等待问题。
2. P0：实现规则标准化和确定性检查器，提升准确率和稳定性。
3. P0：完善 PDF/DOC 规范文件解析，不再只依赖简单文本读取。
4. P1：优化批注定位到 run、表格单元格、页眉页脚。
5. P1：增加前端进度、日志、筛选和人工确认能力。
6. P2：增加 Word 渲染检查，处理真实页码、分页、目录、跨页表格等高级版式问题。

## 五、当前结论

系统已经达到“单机版可运行原型/早期可用版”状态：前端、Java 后端、Python Agent、模型配置、文件保存、LLM 调用、结果下载、Word 原生批注、基础测试链路均已具备。

但若目标是“稳定、准确地检查真实论文格式”，下一阶段不能继续把主要判断都压给 LLM。应把系统升级为“Python 确定性格式检查 + LLM 语义判断和解释生成”的混合架构，这是提升准确率、性能和可控性的关键。
